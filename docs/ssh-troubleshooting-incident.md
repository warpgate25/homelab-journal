# Incident Report & Post-Mortem: SSH Hardening & Authentication Lockout

**Дата:** 31 июля 2026 г.  
**Тема:** Отладка SSH-аутентификации, конфликты конфигураций `sshd_config` и восстановление доступа по паролю.

---

## 🛠️ Введение и контекст

В рамках выполнения работы по базовой защите сервера (**Lab 01: Ubuntu Server Hardening**) были применены строгие настройки безопасности для службы OpenSSH:
* Запрет входа под учётной записью `root` (`PermitRootLogin no`).
* Генерация пары ключей Ed25519 (`ssh-keygen -t ed25519`).
* Добавление публичного ключа в `~/.ssh/authorized_keys`.
* Полное отключение парольной аутентификации (`PasswordAuthentication no`).

После применения настроек возник ряд практических проблем и сетевых коллизий при попытке подключения с рабочей станции под управлением Windows (PowerShell).

---

## 🚧 Возникшие проблемы (Troubleshooting Chronology)

### 1. Конфликт IP-адресов в `known_hosts` (DHCP Dynamic IP & Stale Host Keys)
* **Проблема:** Сервер получил по DHCP новый IP-адрес `192.168.1.202`, который ранее уже использовался в локальной сети другим устройством/виртуальной машиной.
* **Симптом:** При попытке подключения SSH блокировал вход с ошибкой `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`, так как отпечаток (fingerprint) нового сервера не совпал со старой записью для этого IP.
* **Решение:** Очистка конфликтующего отпечатка ключа для адреса `192.168.1.202` из файла `known_hosts`:
  ```powershell
  ssh-keygen -R 192.168.1.202

  2. Ошибка путей к приватным ключам и Permission denied (publickey)
Проблема: Клиент SSH в Windows PowerShell не находил путь к файлу приватного ключа при использовании ключа -i (No such file or directory).

Симптом: Так как вход по ключу не удался, а вход по паролю был жестко заблокирован в конфигах, SSH-сервер сразу разрывал соединение с ошибкой:

Plaintext
kali@192.168.1.202: Permission denied (publickey).
3. Конфликт конфигурационных файлов OpenSSH (sshd_config.d/*.conf)
Проблема: Попытки включить парольную аутентификацию назад через утилиту sed в /etc/ssh/sshd_config не давали результата.

Причина: В современных дистрибутивах Ubuntu Server настройки из директории /etc/ssh/sshd_config.d/*.conf перекрывают (override) основные параметры из sshd_config. Запрещающий параметр PasswordAuthentication no оставался активен в дочерних конфигах.

Дополнительная сложность: Отсутствие общего буфера обмена между хост-системой (Windows) и консолью гипервизора (VirtualBox/VMware), что требовало ручного ввода команд в условиях ограниченного доступа.

💡 Итоговое решение (Resolution Steps)
Для восстановления стабильного доступа по паролю без потери времени на ввод длинных путей к ключам в CLI были выполнены следующие шаги прямо из консоли сервера:

Удаление перекрывающих конфигов:

Bash
sudo rm -rf /etc/ssh/sshd_config.d/*
Явное включение парольной аутентификации в основном файле:

Bash
sudo sed -i 's/PasswordAuthentication no/PasswordAuthentication yes/g' /etc/ssh/sshd_config
Перезапуск службы OpenSSH:

Bash
sudo systemctl restart ssh
🎓 Выводы и вынесенные уроки (Key Takeaways)
Иерархия конфигов OpenSSH: Всегда необходимо учитывать директорию sshd_config.d/. Изменения в главном sshd_config не сработают, если внутри sshd_config.d/ лежат приоритетные файлы.

Баланс безопасности и удобства (Usability vs Security): В лабораторных и учебных средах жесткий отказ от паролей может существенно замедлять процесс разработки при смене сетевых интерфейсов. Ключевая аутентификация должна сопровождаться настройкой статического IP (или резервированием DHCP) и удобных алиасов в ~/.ssh/config.

Troubleshooting Skills: Ошибка Permission denied (publickey) однозначно указывает на то, что сервер не принимает публичные ключи клиента и при этом блокирует запрос пароля.
